## 明确排除与需区分的内容

排除：希伯来语宗教填充、无关多语言声明、拼接常量来掩盖特征字符串、代码混淆服务/长按复制彩蛋、上游自动覆盖脚本、宣传链接、无关动画/地图展示、仿 nginx 或仿 Cloudflare 1101 错误页面。

首页改为真实 Prometheus 页面，缺配置时显示本地配置提示。原 `URL` 伪装首页行为不纳入推荐设计；若确实需要通用站点反向代理，则应作为独立明确功能重新列入。

保留：协议必须的密码与密钥派生、Shadowsocks AEAD、XHTTP padding、链式代理参数编解码、转换服务 token 与真实客户端配置。代码变量和常量可改成直观英文名，但协议字节与旧数据含义保持一致。

第三方公共反代池、转换端和订阅源属于真实外部依赖。建议在配置中显式显示来源，能改成用户自有地址；不把原作者服务默认为“自己的服务”。是否继续保留原默认公共服务需要在设计确认时明确。

## 推荐结构

```text
src/
  router/               页面与导航守卫
  stores/               登录状态、配置、地址库、运行状态
  api/                  类型化 API 客户端
  components/           配置表单、节点链接、日志、检测结果
  views/                登录、概览、配置、地址库、代理、日志、集成
server/
  index.ts              请求分类与路由
  auth/                 会话与旧身份兼容
  config/               模型、默认值、旧 KV 数据迁移与校验
  api/                  管理与诊断端点
  protocols/            vless、trojan、shadowsocks
  transports/           websocket、grpc、xhttp
  network/              socket、dialer、backpressure、dns
  proxies/              proxyip、socks5、http、https、turn、sstp
  crypto/               协议所需算法及确有必要的嵌套 TLS
  subscriptions/        地址来源、链接、转换、客户端补丁
  integrations/         Cloudflare、Telegram
shared/                 DTO、字段类型与受控枚举
 test/                  协议向量、边界、API、流与兼容测试
```

使用当前 Cloudflare Vite 插件生成 Vue assets 与 Worker。旧 `/sub`、`/version`、订阅路径、传输路径和必要旧管理 API 做兼容映射。新管理 API 可放到 `/api/`；Vue assets 的规则必须让 WS/gRPC/XHTTP 及兼容端点先经过 Worker，避免 SPA fallback 吞掉隧道请求。前端仅处理管理交互，不承载服务端密码、代理凭据或加密密钥。

## 技术修正与实施约束

1. 源码 TCP 适配器依赖 `request.fetcher.connect`。Prometheus 应通过 `import { connect } from 'cloudflare:sockets'` 显式注入网络连接器，并按官方平台限制处理失败。
2. 上游 `config_JSON`、DEBUG、拨号数等是模块级可变值，不能把当前请求配置保存在全局对象供其他请求共享；只缓存受控、按键隔离的数据。
3. 凭据只保留在 Worker 环境或 KV。Cloudflare 凭据检测不通过 URL 查询暴露到日志；新 API 用授权请求体，兼容端点单独评估。
4. 会话增强必须与兼容策略一起测试。确认旧 UUID、节点链接、订阅 token 是否仍能使用，不因为登录改造顺带换掉所有客户端身份。
5. 不直接复制 4.8 MB 注释，也不整体打包远端 HTML。源码拆分须有明确模块契约；不能只加 `// @ts-nocheck` 然后声称 TypeScript 重构完成。
6. 继承代码保留 GPL v2 与上游归属。没有把源文件注释中“非开源”声明当作用户要求。
7. 参考代码已有行为可作为差分对照，但必须先把 TCP 适配与外部服务替换为受控测试接口。mock 通过不能替代真实链路可用性验证。

官方 TCP API： https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/

## 备选方案与取舍

A. 整体桥接旧 Worker：最快跑起，但保留单文件耦合、外部 HTML 与全局状态，不能满足完整重构要求；不推荐。

B. 全部协议一次从零重写：代码可以更干净，但兼容性回归风险最高，难以逐项证明等价；不推荐作为唯一策略。

C. 推荐：以功能矩阵为边界逐模块迁移，先建立旧行为与协议向量测试，再重构后端与本地 Vue 管理页。可以暂时沿用已验证的协议算法实现，但必须移除无关填充、建立类型契约并消除原单文件的全局状态依赖。

## 验收方式

- 每项模块有迁移位置、相应测试及通过/失败/待验证状态。
- 协议向量：正确/错误 UUID、密码、AEAD tag、分片首包、IPv4/IPv6/域名、错误命令、过长早期数据、nonce 和响应头。
- 流与代理：重拨、并发、背压、取消、队列上限、失败清理；五类代理握手和回退有受控测试。
- 管理端：登录/注销、未授权拒绝、配置保存/重置、地址库与日志、敏感字段脱敏、页面刷新与错误展示。
- 订阅：各协议链接、客户端格式、参数选项、地址源失败、转换专用 token、客户端补丁快照。
- 构建：前端/后端类型检查、测试、生产构建、Wrangler dry-run；部署前人工批准。
- 真实 Workers 环境完成已配置协议的端到端连接。没有账号、KV 或外部代理凭据时，标注真实测试缺口，不以构建成功代替所有网络功能验收。
- 新代码与产物不含宗教填充、混淆服务调用或运行时远端管理页面加载。
